# Development, update and public-route checkpoints

This is a decision runbook, not authority to install, build, deploy, restart or publish. The [operator guide](operator-guide.md) has the owner UI sequence; [release preparation](release-preparation.md) has exact source-only commands. Never run commands below against a live pier or infer target acceptance from source tests. Keep private installation identifiers, logs, credentials, tokens, personal domains and certificates out of public issues.

## Private package artifact and update

**Maintainer, offline/source-only:** From an approved checkout, use Node >=20, Python 3 and an **already installed** SDK 0.3.55, setting `DAPPNODE_SDK_ROOT` to its directory. Set the private, existing scratch variables exactly as in [release prerequisites](release-preparation.md#prerequisites). Run the focused source tests there. A non-Docker descriptor-only preview may be made with `RELEASE_OUTPUT` set to a new absolute external directory, then `npm run prepare:release -- --output "$RELEASE_OUTPUT"`. Check `inventory.json` hashes, expected tag/architecture and `DESCRIPTORS_ONLY_IMAGE_UNBOUND`; it is **not an image or installable bundle**. Do not run `npm run validate` expecting a no-Docker check. If the SDK is missing, stop; do not silently install dependencies or substitute a different version. Never retag the canonical 0.1.3 descriptors as if they were the installed private 0.1.4/0.1.5 derivatives.

**Maintainer delivery gate:** An approved actual image/descriptor bundle must match service `ship`, package `uvm.public.dappnode.eth`, architecture, image tag, selected feature record and persistent volume mapping. The supported custom/dev installer is Dappmanager-version-dependent; there is no repository command or generic web-upload button here. Confirm the actual delivery method with the maintainer and obtain owner approval for that exact target/artifact. Do not upload descriptors alone, use Dappmanager File Manager for image/pier delivery, disable release checks, or infer installed provenance from a source version. Distribution requires the separate [licensing/signing gates](distribution-review.md).

**Owner target readback:** Before change, read package/image identity and mount metadata through the trusted target management UI without opening private state; confirm `ship_data:/urbit` points to the intended existing UVM volume. An old package's similarly named volume is *not* interchangeable ([migration](migration.md)). Preserve the accepted artifact and a sufficiently current verified stopped-state backup. If mount or feature identity is uncertain, do not proceed. After an approved installation, verify private HTTPS, normal UVM login, existing import READY_LOCKED and runtime STOPPED before any Start. Repeat enrollment or certificate exchange only for a genuinely fresh namespace, never to fix an update. Stop on `VOLUME_LAYOUT_REFUSED`, `FAULT` or `RECOVERY_REQUIRED`; retain all state for reviewed recovery.

## Optional Dappmanager MCP access

This is an **external development-client** path, not a UVM feature or a prerequisite for a running ship. [Dappnode's MCP guide](https://docs.dappnode.io/docs/dev/package-development/agent-assisted-development/) requires Dappmanager v0.2.125+, private access (e.g. VPN) and admin UI access. Its MCP API key authenticates `/mcp` and is **not** the Nexus Chat API key, UVM enrollment authority, ship code or tunnel token. No repository file or chat transcript should carry it. The guide's `System > Advanced > MCP API key` page documents owner-operated generation; the raw key is displayed only when generated. The owner enters a new value directly into the client's protected credential workflow. If rotation is required, first confirm the actual Dappmanager version's supported regeneration/revocation semantics and plan an owner-only change and client reconnection window; do not assume a second Generate click safely rotates an existing key. Do not ask an agent to reveal, transfer, test, paste or regenerate a key. Key lifetime, revocation/readback and target-specific rotation remain unverified here.

**Three distinct switches/gates:**

1. **Dappmanager authorization (target-side):** read-only MCP tools are available by default. For a separately approved package-changing workflow, the owner may enable **Allow mutating MCP tools** on the same Dappmanager page, verify the saved state there, and disable it again when finished. This is not a switch for the UVM container or public tunnel. Leave it off for ordinary audit/read access. A tool's name appearing in discovery does **not** establish this gate is open or that a write is approved.
2. **Hermes MCP server (client-side, per profile):** select the intended profile explicitly; the dashboard's profile switcher must point at that profile before its MCP page's enable/disable action. A disabled server remains configured, but is not loaded on the next gateway restart; a current session may require its supported MCP reload to refresh discovery. `hermes --profile cancelbot mcp list` is a nonsecret status check (do not copy endpoint fields into reports). The existing `cancelbot` profile showed `dappnode` enabled and 11 selected tools at audit time; it is **not** the active `default` profile. Do not toggle either profile without approval.
3. **Hermes individual-tool selection (client-side):** `hermes --profile cancelbot tools list --platform cli` reports the selected names, including developer upload/install tools; `hermes mcp configure dappnode` and `hermes tools enable/disable --platform cli dappnode:TOOL` are configuration-changing actions, **not** readback commands. Check the current `--help` and target session's exposed schemas before any separately authorized change. Selection is neither a Dappmanager mutation grant nor owner approval of an actual call.

**Nonsecret verification/stop gate:** owner checks the target UI's current **Allow mutating MCP tools** state without disclosing key or screenshots of secrets; operator confirms intended Hermes profile/server status and selected names with the commands above, then (only if separately permitted) tests transport/tool discovery in that profile with `hermes --profile cancelbot mcp test dappnode`. Prior discovery succeeded; it did not test a write. Confirm actual task-session availability separately. For a write, obtain approval for the exact artifact/target/mount and action, then read back its nonsecret outcome by an independent target management view; never use upload/install as a permission probe. If target toggle/readback, version, selected profile or tool schema is unknown, **stop**. This audit did not inspect the live Dappmanager toggle, rotate a key, change any switch or confirm a target write. See [audit](workflow-audit.md) for evidence and gaps.

## Stopped-state update and recovery boundary

1. Owner uses private UVM **Stop managed ship**, then refreshes until **STOPPED**; independently ensure no other writer or auto-restart. A Stop click or container badge is not enough. If status is uncertain, pause; do not take a snapshot or install.
2. Owner verifies the stopped backup's recency and restore plan separately, preserving original storage. Issue [#7](https://github.com/OwlWilderness/dappnode-urbit/issues/7) owns any new backup implementation; no generic live-volume tar or automated restore is endorsed here. Import into fresh managed storage follows [operator §5](operator-guide.md#5-import-the-stopped-pier-then-explicitly-start): one top-level stopped ZIP, UVM browser transfer, READY_LOCKED, explicit single-instance Start.
3. With explicit owner approval, use only a qualified matching update and preserve the volume, TLS identity and enrollment. Read back the installed identity, mount and private access after replacement. Confirm runtime remains STOPPED. Owner then confirms the single-instance rule and explicitly Starts once; refresh status before retry, and verify private ship login (RUNNING is only process state).
4. On failure, **stop retries**. Keep previous image and state; identify whether failure is source, container, UVM login, ship boot or public route. An image-only rollback, if separately approved and qualified, does **not** reverse pier changes or repair incompatible persisted state. Do not reset TLS/auth, delete journals, force volume adoption, restore a stale backup over current state or start another instance. Escalate with nonsecret state labels only.

## Optional public route

Use [public access](public-access.md#prepare-and-activate) for the UVM backend, and the companion repository's [origin route contract](https://github.com/OwlWilderness/dappnode-urbit-ship-tunnel#origin-route-contract) for authoritative connector settings. No token, public CA file, tunnel, DNS or route is provided by either source checkout. An approved connector image contains **only the public owner CA certificate**; the owner privately supplies the named tunnel token in Dappnode (not source/chat/CLI). Confirm dedicated UVM backend on 9444 is ready before publishing a route; private manager/ship 8443 is never a tunnel target.

Owner configures a **single exact ship hostname** with HTTPS backend, exact HTTP Host header, private origin SNI, pinned public CA pool, TLS verification enabled and no wildcard/admin fallback. Read back the saved effective route and investigate the unverified catch-all rather than assuming `404`. Check connected replica, strict backend TLS, public `/~/login` 200, admin-path isolation, then owner-only login and application EAuth return separately. A tunnel connection or HTTP 200 alone proves neither login nor EAuth; investigate discovery, redirect, approval and return as distinct stages. For 502 check actual ship readiness before changing TLS. Do not relax verification, add plaintext fallback, inspect credentials or restart Vere to make a probe pass.

For withdrawal, disable the public route or connector first; DNS removal alone is not immediate. Preserve private manager access and the original volume. Edge/origin renewal, catch-all readback, broad API/WebSocket behavior and Ames/UDP remain unqualified. No automatic DNS/token rotation or recovery is specified.
