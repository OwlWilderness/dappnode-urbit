# OpenSSL allocation/cleanup functional-parity audit

## Decision and boundary

**Source audit complete; allocation parity NOT established.** Retain OpenSSL 3's default process heap. Do not restore the temporary-road allocator hook. Context-constructor hardening alone is insufficient: SHA one-shot operations introduce a concrete new allocation-failure surface; H2O connection objects and nonlocal exits also need coverage.

This is a finite review of allocation boundaries reached by Vere's OpenSSL integration, not a rewrite of all Vere memory management or an exhaustive audit of OpenSSL internals. No production files were changed; no tests, builds, executable, controllers, containers or ship were run. No private state/logs/keys were read. Closed attempts and retired ARM artifacts were not replayed. The implementation worker owns editable recipe/tests; this document describes the **accepted archived source**, not that worker's evolving patch.

Historical evidence was read from `openssl-amd64-tls-result.md`, `openssl-amd64-allocator-result.md` and `openssl-arm64-allocator-result.md`. Their observed outcomes remain distinct: source characterization identified missing guards; synthetic libc allocation established accounting visibility; prior allocator intervention supports a lifetime incompatibility but does not identify every stale object or prove failure recovery. No new runtime claims are made here.

## Allocator/lifetime delta

Before: `_cm_malloc_ssl`, `_cm_realloc_ssl`, `_cm_free_ssl` forward to `u3a_*` (`V/pkg/noun/manage.c:2469–2503`); hook installation was unconditional except `U3_URTH_MASS`. `u3a_malloc/realloc` allocate in the current road (`allocate.c:232–249,307–385`). Allocation pressure can reclaim memo cache and bail with `meme` (`204–224`), rather than supply ordinary libc-style NULL to OpenSSL. This is not evidence that OpenSSL safely tolerates the nonlocal exit.

After: `manage.c:2512–2521` excludes OpenSSL >=3 from that hook; GMP setup remains at `2555`. `O/crypto/mem.c:188–237,302–365` uses ordinary allocation/NULL propagation; realloc failure retains the old allocation, zero-size realloc frees, and ordinary free is not cleansing. Default-heap allocations do not become road-owned merely because their caller executes on a road.

`u3m_love` copies noun products/caches then rewinds the road (`manage.c:1350–1387`). It does not discover C library ownership or invoke destructors. Thus the original hook could reclaim operation storage but also invalidate retained OpenSSL globals/TLS/provider state. The new heap fixes that lifetime mismatch, but storage reachable only through an abandoned C stack is no longer reclaimed by the road. Normal OpenSSL cleanup (`O/crypto/init.c:93–114,374–412`) is not a registry for every leaked application-owned object.

Ordinary bail and signal paths are separate: `_setjmp` around computation at `manage.c:1520–1545`; `u3m_signal` performs `rsignal_longjmp` at `448–450`, returning through the top-level recovery at `1496–1507`. A signal while inside OpenSSL/libc may abandon both allocations **and internal locks/state**. Freeing a few outer pointers after a jump is not proof of safe recovery from interruption inside a non-async-signal-safe library. This hazard predates the upgrade; off-road lost allocations and changed provider activity expand its consequences. Do not assume event-loop HTTP/curl calls run under the worker's same signal regime: trace and test each caller separately.

## High-confidence findings and priorities

1. **P0 — upgrade-induced SHA failure exposure.** Baseline OpenSSL 1.1.1w `sha1_one.c:15–27`, `sha256.c:63–74`, `sha512.c:340–351` use stack contexts. Accepted `O/crypto/sha/sha1_one.c:38–80` routes SHA1/256/512 through `EVP_Q_digest`. `O/crypto/evp/digest.c:726–758` fetches a digest and allocates an `EVP_MD_CTX`; either can fail without writing the digest. `U/urcrypt/sha.c:5–47` ignores returns, including nested salted hashing. Vere then consumes uninitialized stack output (`V/pkg/noun/jets/e/sha1.c:17–22`, `shax.c:20–24,31–36,48–52,60–68`; also `pkg/noun/jets.c:131`). This is a newly reachable allocation-failure path under unchanged wrappers, not merely a missing style check. Require checked propagation through every caller or a deliberately reviewed nonallocating digest implementation preserving bytes. Never substitute a zero digest as success.
2. **P0 — context allocation NULL is used immediately.** `cttp.c:973–983` and `http.c:2375–2387` call setters after unchecked `SSL_CTX_new`; `O/ssl/ssl_lib.c:6309–6312` dereferences the context. Missing guards are inherited; returning NULL rather than road-bailing makes ordinary heap OOM behavior materially different. The previously executed characterization is not a recovery pass.
3. **P1 — H2O connection allocation remains unsafe beyond contexts.** `H/lib/common/socket.c:925–929` calls `setup_bio` after unchecked `SSL_new`; `215–238` uses unchecked `BIO_meth_new` in setters. `BIO_new` is **checked**, but invokes `h2o_fatal` rather than connection-level recovery. The distinction matters: not every site is an unchecked NULL. `create_ossl` is reached by client handshake (`1210`), server fallback (`1088–1089`) and resumption recreation (`1117–1118`). These inherited dependency call patterns require explicit outcome tests under the new allocation model.
4. **P1 — failed extra-chain insertion loses ownership.** `http.c:2437–2440` ignores `SSL_CTX_add_extra_chain_cert`. `O/ssl/s3_lib.c:4538–4547` returns failure if stack creation/push fails without taking the supplied certificate. The loop overwrites its local pointer, losing that `X509`; it also returns a potentially incomplete context. Inherited unchecked transfer, now a native-heap leak on this path. Free on failed transfer and fail construction; do not free a successful transfer twice.
5. **P1 — preexisting cttp shutdown use-after-free affects TLS cleanup.** `cttp.c:1111–1113` reads `ceq_u->nex_u` after `_cttp_creq_quit`; for non-resolving requests `_quit:699–710` calls `_free:517–535`, which frees `ceq_u`. This is directly visible in unchanged source, not caused by OpenSSL 3. Include it in TLS cancellation/shutdown tests; save the next pointer before a potentially freeing call and separately account for pending DNS callbacks/driver lifetime.
6. **P2 — inherited curl-wrapper leaks, not OpenSSL-allocator regressions.** `dawn.c:68–70` overwrites the slist head on append failure (`C/lib/slist.c:85–96` returns NULL). `king.c:383–390` overwrites an existing body allocation on another Content-Length header; `400–452` returns transfer/HTTP failure without freeing its buffer and reuses partial state across retries. These buffers were already `c3_*`/curl-owned, not allocations moved by the OpenSSL hook. Include narrow fixes/tests if touching those boundaries; do not describe them as proof of new SSL leaks.

## Conditional/transitive surface: bounded exclusions, not hidden passes

- `H/lib/handler/configurator/proxy.c:85–125,144–155,302–326` has additional SSL_CTX/X509_STORE allocation and ownership transfers, including an unchecked context constructor. It is listed by the build, but inspected Vere server setup (`http.c:2166–2230`) uses direct registration, not YAML proxy configuration. Establish reachability before treating it as a live Vere failure. Do not declare it safe or expand this into generic H2O configurator hardening without that evidence.
- H2O picotls OpenSSL adapter is compiled by `V/ext/h2o/build.zig:284–301`. Normal reviewed Vere setup assigns an SSL_CTX without installing a picotls context. Backend activation/reachability must be established before claiming coverage of its EC/EVP/X509 allocations. H2O cache-digest/casper hashing uses low-level stack SHA contexts (`H/lib/http2/cache_digests.c:150–153`, `casper.c:40–47`). `H/lib/websocket.c:36` has one-shot SHA, but that file is absent from the inspected H2O source list; do not equate archive presence with executable reachability.
- curl has additional EVP contexts in `C/lib/{md4.c:52–72,md5.c:83–106,sha256.c:64–87,curl_ed25519.c:58–79}`. Constructors/init generally have checks; some digest update/final calls discard results. `V/ext/curl/build.zig:28–67` disables many auth/protocol features including NTLM, Digest, AWS and proxy, while listing these files later. TLS-internal digest/KDF/certificate allocations are covered at returned-error boundaries, not independently proven allocation by allocation. Before a whole-library claim, bind active macros and actual callers for these helpers; fault their live paths or record them unreachable. QUIC/Windows/optional certificate/engine/provider configuration paths are not accepted solely because source exists.
- urcrypt's secp256k1, ed25519, scrypt/PBKDF2, Argon, Keccak, Blake and ChaCha wrappers use separate libraries selected in `V/ext/urcrypt/build.zig`; they are not automatically OpenSSL allocations. For example `U/urcrypt/scrypt.c:14–30` calls libscrypt. Their unrelated allocator redesign is outside this task.

## Closure criteria and implementation handoff

Prioritize A09, A02–A07, then actual cancellation/nonlocal-exit coverage A08/A14; retain A10–A13/A15–A16 as explicit finite obligations. P0 SHA handling and H2O SSL allocation are important findings for the parent/implementation worker, not reasons to overwrite their recipe or tests from this audit.

A scoped patch may accurately claim particular rows hardened when actual unchanged/modified functions and callers pass deterministic negative tests. It may not claim “all allocation parity restored” based on regex checks, mocks of constructors only, prior boot success, or synthetic libc RSS. Native dependency internals require appropriate fault injection/leak tooling and the actual target build; safe signal recovery needs its own proof. Exact accepted `.a` files remain unavailable according to the TLS result; this archive metadata corroborates their absence here, not their destruction everywhere. No rebuild or runtime was authorized by this audit.

Preserve the accepted binary and closed attempts. Functional parity means correct cryptographic results, explicit failure rather than fabricated success, valid object lifetime/ownership, bounded resources under the chosen failure policy, and honest total-memory visibility. It does **not** mean recreating unsafe original allocator behavior or fixing every preexisting Vere defect.

Tooling limitation: repository-local `docs/resume.md`, `docs/backlog.md` and the two named `.agents/skills/.../SKILL.md` paths were absent in this task checkout; available container-package-development and systematic-debugging skills were loaded. The documentation extraction backend refused URL extraction; pinned primary public source was retrieved directly instead. Neither limitation was treated as runtime evidence.
